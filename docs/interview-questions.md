## 一、基础概念（8 题）— 考察测试思维是否清晰

### Q1
**"如果明天这个电商系统要上线，你是测试，你告诉我能不能上？凭什么？"**

> 考点：是否理解"测试不是拍脑袋说能上就能上"，有没有量化指标意识

- 项目中实际数据：95 条用例全部通过、8 个缺陷全部修复并回归验证、P95 最差 405ms（登录 BCrypt）

### Q2
**"你简历上写了 pytest，请讲一下 pytest 的 fixture 是什么？scope 参数有哪几种？你项目里怎么用的？"**

> 考点：是否真的写过 pytest，还是只背了概念

参考答案要点：
- fixture = 测试前置准备 + 后置清理，类似 JUnit 的 @Before/@After 但更灵活
- scope: `function`（每个测试）→ `class` → `module` → `session`（全测试一次）
- 我们项目的实际用法：`auth_token` 用 `scope="session"` 只登录一次，15 条冒烟测试共享；`client`/`auth_client` 用默认 function 级保证隔离
- yield 前是 setup，yield 后是 teardown

---

### Q3
**"什么是冒烟测试？冒烟测试和回归测试有什么区别？"**

> 考点：是否理解测试分层

参考答案要点：
- 冒烟：验证"系统能不能喘气"——最核心链路，提交即跑，秒级，失败则拒绝本次构建
- 回归：验证"改完代码有没有把别的功能搞坏"——覆盖面更大，日常构建跑，分钟级
- 我们项目：Smoke 15 条（注册登录+商品浏览+加购+下单），Regression 67 条（加上参数校验+权限+状态机主路径），Full 95 条（全量）
- 核心区别：目的不同（冒烟=快速失败 vs 回归=变更影响分析）、执行频率不同、规模不同

### Q7
**"你用过哪些 HTTP 方法？POST 和 PUT 有什么区别？"**

> 考点：REST API 基本素养

参考答案要点：
- 我们项目用了：GET（查询）、POST（创建）、PUT（更新）、DELETE（删除）、OPTIONS（预检）、HEAD
- POST vs PUT：POST 用于创建（幂等性不保证），PUT 用于更新/替换（幂等：多次相同请求效果相同）
- 项目例子：POST /api/orders 创建订单，PUT /api/orders/{id}/status 更新订单状态

### Q8
**"SQL 注入是什么？你怎么测试一个登录接口有没有 SQL 注入漏洞？"**

> 考点：安全测试基础

参考答案要点：
- 用户在输入里嵌入 SQL 语句，如果后端拼字符串构造 SQL 就会执行恶意代码
- 测试方法：用 payload 列表（`' OR '1'='1`、`'; DROP TABLE users; --` 等）作为用户名/密码输入
- 正常防护结果：参数化查询，payload 被当作普通字符串，返回 401（而非 200 绕过登录或 500 崩溃）
- 本项目 security_test.py 里有 13 条 SQL 注入测试，全部通过

### Q10
**"看这段代码，有什么问题？"**

```python
def test_login(self):
    resp = requests.post("http://localhost:8080/api/auth/login", json={
        "username": "testuser1",
        "password": "Test@123456"
    })
    assert resp.status_code == 200
```

> 考点：是否具备代码审查意识

参考答案要点（至少说 3 个）：
1. **硬编码 URL**：BASE_URL 没有统一管理，换环境要改所有用例
2. **没有用封装的 ApiClient**：重复代码，断言不够（只检查了 HTTP 200，没检查 body 里的业务 code）
3. **依赖执行顺序**：必须先注册 testuser1，用例间有隐式依赖
4. **没有标记**：不知道这条用例属于 smoke 还是 full
5. **没有关联 TC-ID**：失败了不知道对应 RTM 里哪条用例
6. **没有 docstring**：不知道这个测试到底测什么

### Q11
**"pytest 的 parametrize 是什么？你项目里怎么用的？"**

> 考点：是否会用参数化减少重复代码

参考答案要点：
- `@pytest.mark.parametrize` = 一条测试逻辑 × 多组数据，避免写 N 条几乎一样的用例
- 项目中的实际用法：
  ```python
  # security_test.py: 6个SQL注入payload × 2个场景 = 12条用例，只写2个方法
  @pytest.mark.parametrize("payload", ["' OR '1'='1", "' OR '1'='1' --", ...])
  def test_login_sqli(self, client, payload):
      ...

  # test_auth_security.py: 6个接口 × 1条逻辑 = 6条用例，只写1个方法
  @pytest.mark.parametrize("method,path,data", [
      ("GET", "/cart", None),
      ("POST", "/cart/items", {...}),
      ...
  ])
  def test_unauthorized_access(self, client, method, path, data):
      ...
  ```

### Q12
**"你做接口自动化时，怎么处理'登录态'？每次测试都重新登录吗？"**

> 考点：是否理解 fixture scope 的实际应用

参考答案要点：
- 不。用 pytest fixture `scope="session"`：整个测试 session 只登录一次，token 共享给所有用例
- 具体实现见 conftest.py：`auth_token` fixture 登录后返回 token，`auth_client` fixture 自动带上 `Authorization: Bearer <token>`
- 好处：15 条用例省 14 次登录，而且测试速度更快
- 但要注意：token 过期的问题——短 token 用 function 级；我们项目 token 24h 有效，session 级没问题

### Q13
**"自动化测试是不是越多越好？什么时候不适合写自动化？"**

> 考点：是否有成本意识，而非"一切皆自动化"

参考答案要点：
适合：重复执行（回归）、数据验证（需要查 DB）、大量参数组合（parametrize）、CI 集成
不适合：
- UI 视觉验证（"这个蓝色对不对"——人眼判断）
- 一次性探索测试（写脚本比跑一遍还慢）
- 频繁变化的界面（维护成本 > 收益）
- 用户体验评估（"这个流程顺不顺手"）
- 验证码 / 生物识别

## 三、接口测试与 Postman/Newman（5 题）

### Q17
**"Postman 里的 Pre-request Script 和 Tests 脚本分别是干什么的？你项目里怎么用的？"**

> 考点：是否真正用过 Postman 的高级功能

参考答案要点：

**"你们用 Newman 做什么？和 pytest 测试有什么区别？"**

### Q19
**"一个接口有 5 个必填参数，你打算怎么设计测试用例？"**

> 考点：是否会用组合测试方法

参考答案要点：
- 正向：1 条（全有效）
- 每个必填参数缺失：5 条（逐一缺失，验证独立校验）
- 全部缺失：1 条
- 边界值：每个字段的有效/无效边界（取决于字段类型）

### Q20
**"RESTful API 设计中，响应体应该包含什么字段？你们项目的统一响应格式是怎样的？"**

> 考点：API 规范意识

参考答案要点：

### Q21
**"API 测试中，怎么验证'数据真的被修改了'？只看返回值够不够？"**

> 考点：是否理解"数据层验证"的重要性

参考答案要点：
- 不够。API 返回 200 只说明没有异常，不代表数据真的写入了
- 必须做**数据层双验证**：
  1. API 返回值验证

## 四、性能测试（5 题）

### Q22
**"如果一个接口在高并发下变慢了，你会从哪些角度排查？"**

> 考点：性能问题的系统化分析能力

参考答案要点：
- 先定位瓶颈在哪一层：应用层？数据库层？网络层？
- 数据库：慢查询日志 → 索引是否命中 → 连接池是否够 → 锁等待
- 应用：CPU/内存 → 线程池 → GC → 同步锁竞争
- 网络：带宽 → 延迟
- 具体例子：我们项目登录接口 P95 405ms（500 并发），原因是 BCrypt 密码哈希计算本身就是 CPU 密集型操作，这是**设计上的安全特性**而非缺陷

---

### Q23
**"TPS 和响应时间是什么关系？TPS 越高越好吗？"**

> 考点：是否真正理解性能指标

参考答案要点：
- TPS（Transactions Per Second）= 每秒处理的事务数
- 响应时间 = 单个请求从发起到收到响应的时间
- 关系：在资源饱和前，增加并发 → TPS 上升 + 响应时间也上升；饱和后 → TPS 平稳 + 响应时间飙升
- TPS 不是越高越好：要看业务需求（登录不需要 5000 TPS），也要看响应时间是否在阈值内（P95 < 2000ms）
- 我们的数据：商品列表 50并发 TPS=1591, 500并发 TPS=4974 → 读操作扩展性良好

---

### Q24
**"P50、P95、P99 是什么意思？为什么不能只看平均值？"**

> 考点：是否理解百分位数指标

参考答案要点：
- P50 = 中位数：50% 的请求在这个时间内完成
- P95：95% 的请求在这个时间内完成 → 线上 SLA 通常以 P95/P99 为标准
- P99：99% 的请求
- 为什么不能只看平均值：如果有 99 个请求 10ms + 1 个请求 5000ms，平均值 = 59.9ms（看起来很好），但 P99 = 5000ms（1% 用户等了 5 秒！）
- 项目里 perf_test.py 实现了 `percentile()` 函数计算所有百分位

---

### Q25
**"你用 Python 做压测，和 JMeter 比有什么优缺点？"**

> 考点：工具选择是否有逻辑依据

参考答案要点：
| | Python 脚本 | JMeter |
|------|---------|--------|
| 灵活性 | 高（任意逻辑，如动态构造数据） | 中（GUI 配置为主） |
| 学习曲线 | 需要编程能力 | GUI 上手快 |

### Q26
**"我们的订单接口在高并发下是怎么防止超卖的？原理是什么？"**

> 考点：是否理解并发控制机制

参考答案要点：
- MyBatis-Plus 的 `@Version` 注解实现乐观锁
- 原理：UPDATE products SET stock = stock - ? WHERE id = ? AND version = ?
  - 如果两个请求同时读到 version=5
  - 第一个更新成功 → version 变成 6
  - 第二个更新 WHERE version=5 找不到记录 → 更新失败 → 抛 OptimisticLockException → 订单回滚
- 我们的验证方式：perf_test.py S-PERF-05 场景，设置有限库存（stock=并发数/2），验证只有一半的订单能成功

## 五、安全测试（5 题）

### Q27
**"你了解 OWASP Top 10 吗？列举几个你实际测试过的。"**

> 考点：安全测试是否有实操经验

参考答案要点（本项目实际测试过的）：
- **A1 SQL 注入**：13 条用例，6 种 payload × 登录/搜索 + 路径参数，全部通过（参数化查询防护）
- **A2 敏感信息泄露**：3 条用例，确认登录响应不返回密码、错误响应不泄露堆栈
- **A3 XSS 跨站脚本**：8 条用例，4 种 payload × 注册/搜索，验证不反射 script 标签
- **A5 越权访问**：普通用户不能执行发货操作（验证 403）
- **A6 安全配置错误**：CORS 检查（当前 dev 配置为 *，已知限制）
- **A7 认证失败**：JWT 篡改/损坏/空值全返回 401，Basic Auth 被拒绝

### Q28
**"JWT Token 是什么？你怎么测试 Token 的安全性？"**

> 考点：是否理解认证机制

参考答案要点：
- JWT = 三段式：Header.Payload.Signature，签名防止篡改
- 测试维度：
  1. 无 Token → 401（test_unauthorized_access，6 个接口参数化）
  2. 篡改 Token（改 payload 但签名不匹配）→ 401
  3. 损坏 Token（"not.a.token"）→ 401
  4. 空 Token（""）→ 401
  5. 错误格式（Basic Auth 而非 Bearer）→ 401
- 全在我们项目的 test_auth_security.py 里

### Q29
**"用户密码应该怎么存储？你怎么验证密码没有被泄露？"**

> 考点：安全编码意识

参考答案要点：
- 必须 hash 存储（BCrypt/Argon2），绝不能明文或可逆加密
- 测试验证：
  1. 登录响应里不应包含 password 字段（test_login_response_no_password）
  2. 获取用户信息不应返回 password hash（test_user_info_no_password）
  3. 错误响应不应泄露加密方式（如 "bcrypt" 字样）
- BCrypt 慢是故意的：故意增加计算成本来抵抗暴力破解。这就是为什么我们登录 P95 是 405ms——功能正常，不是 Bug

### Q30
**"你怎么区分'安全漏洞'和'功能缺陷'？"**

> 考点：Bug 定级能力

参考答案要点：
- **功能缺陷**：系统行为不符合需求。如：数量为 0 仍可下单（BUG-007），这不安全但主要是功能 bug
- **安全漏洞**：可能导致数据泄露、权限绕过、系统被攻击。如：SQL 注入能获取全表数据、普通用户能操作其他用户订单
- 定级参考：
  - 安全漏洞通常定级更高（P0/P1），因为影响面不只是功能不可用，而是数据安全
  - 本项目 8 个 Bug 都是功能缺陷（87.5% 是缺少输入校验），安全测试 29 条全部通过（1 条 CORS=* 已知限制除外）

### Q31
**"CSRF 和 XSS 有什么区别？API 项目需要担心 CSRF 吗？"**

> 考点：安全知识广度

参考答案要点：
- XSS：注入脚本到页面，利用用户浏览器执行恶意代码
- CSRF：诱导用户点击链接，利用用户已有的登录态发起非预期请求
- API 项目（JWT Bearer Token 认证）**通常不需要担心传统 CSRF**：
  - CSRF 依赖浏览器自动带 Cookie
  - JWT 用 Authorization Header，浏览器不会自动带
  - 但如果 JWT 存在 Cookie 里（而非 Header），CSRF 风险仍然存在
- 我们的项目：JWT 通过 Header 传递，前端用 Axios interceptor 自动添加

## 六、综合场景题（5 题）— 考察解决实际问题的能力

### Q32
**"假设你是这个项目唯一的测试，开发每周五下午 5 点提测，说'周一要上线'。你怎么安排测试？"**

> 考点：时间管理 + 风险评估 + 测试策略

参考答案要点：
1. **先跑冒烟**（15 条，1 秒）：核心链路能不能走通？不通直接打回
2. **回归验证**（67 条，2 秒）：上次提测修了哪些 Bug？验证修复 + 检查有无新引入问题
3. **缺陷复测**：检查已修复的 BUG-001~008 是否真正修复
4. **风险评估**：本次改了哪些模块？（改订单 → 重点回归订单状态机 + 库存扣减；改用户 → 重点回归注册/登录/权限）
5. **时间不够时**：优先 P0 用例 + 变更影响范围内的用例，非核心模块降低优先级
6. **底线**：P0 阻塞缺陷必须清零（不能带着已知严重 Bug 上线）

### Q33
**"你发现一个 Bug：用户名输入 `<script>alert(1)</script>` 注册后，在个人中心页面弹了窗。这个 Bug 的根本原因是什么？应该由谁修？怎么验证修好了？"**

> 考点：跨层分析能力（前端+后端）

参考答案要点：
- 这是**反射型 XSS**
- 根因可能有两层：
  1. 后端没有对输入做校验/转义（我们的项目有 `@Pattern` 限定了用户名格式，所以 XSS payload 会被拒绝在注册阶段）
  2. 前端渲染时没有对用户输入做转义（Vue 的 `{{ }}` 模板默认转义，但 `v-html` 不会）
- 修复责任：**后端 + 前端都要修**
  - 后端：输入校验 + 输出编码（防御深度）
  - 前端：用 `{{ }}` 而非 `v-html` 渲染用户内容
- 验证：用 `XSS_PAYLOADS` 列表在注册 + 搜索接口参数化测试，确认不反射

### Q35
**"你之前提到 BUG-006：'下单成功但库存未扣减'，这个 Bug 如果不是自动化发现的，手工测试要多久才能发现？为什么？"**

> 考点：是否真正理解了自动化的价值

参考答案要点：
- 手工大概需要 5 分钟以上，而且容易**漏掉**
- 原因：
  1. 手工测试只看界面——订单创建成功页面显示"下单成功"，人不会再打开数据库查 `products` 表确认库存少了没
  2. 自动化直接查了数据库：`old_stock = db.get_product_stock(1)` → 下单 → `new_stock = db.get_product_stock(1)` → `assert new_stock == old_stock - 2`
  3. 这就是**数据层验证**的价值——API 返回 200 不等于数据真的写对了
- 自动化另一个好处：这个 Bug 修完后，每次回归都自动验证，保证不会再犯

### Q39
**"这个 Bug 报告有什么问题？请修改。"**

> 给出一个有缺陷的报告，让候选人挑毛病

```
Bug: 登录不了
严重程度: 高
复现步骤: 输入用户名密码，点击登录，报错了
期望: 能登录
实际: 登录不了
```

参考答案（挑毛病）：
- 标题不具体（"登录不了" → 应该描述现象：如"正确密码登录被拒绝"或"错误密码无提示"）
- 没有复现环境信息（数据库状态？用的哪个账号？）
- 复现步骤不具体（用户名是什么？密码是什么？每一步点了什么？）
- 期望和实际太模糊（期望 HTTP 200 + 返回 token；实际 HTTP 401 + 错误信息是什么）
- 缺少日志/截图/请求响应内容

### Q40 — 开放题
**"给你一个全新的接口：GET /api/products/recommend?userId=1。你没见过文档。你会怎么测试它？说说你的思路。"**

> 考点：探索测试 + 测试设计能力

参考答案要点：
1. **先探索**：不带参数调一次，看返回什么（了解基本行为）
2. **正向**：有效 userId，验证返回格式 + 数据合理性（推荐商品应该有 name/price/image）
3. **参数校验**：userId 为空、userId=-1、userId="abc"、userId=不存在的用户、不传 userId
4. **权限**：不带 token 能不能调？userId 传别的用户 ID 会不会返回别人数据？
5. **业务逻辑**：新用户（无购买记录）返回什么？老用户推荐是否个性化？
6. **性能**：大数据量下响应时间？
7. **边界**：userId=0、userId 超大值、SQL 注入 payload
